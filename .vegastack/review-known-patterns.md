## Cooperative same-UID private run-directory publication

- **Pattern:** a reviewer flags the final `lstat(destination)` followed by portable directory `rename(staging, destination)` in the private run store solely because a malicious process already running as the run-owner OS UID can create an empty destination during that final interval, and requires a native exclusive-rename helper or storage redesign.
- **Why it's safe here:** the operator selected cooperative-owner semantics for this cross-platform Node CLI after the exact residual was surfaced. The run root and staging directory are owned by the current UID with mode `0700`, `run.json` is `0600`, cooperating creators serialize through an exact process-identity claim, any destination visible at the final check is preserved, a non-empty destination makes the directory rename fail, and published bytes are read back exactly. The residual does not cross a user or provider boundary: code already executing as the run-owner UID can replace that private record after publication. Cost if the assumption is wrong: that same-UID process can have its raced empty directory replaced by the verified staged record during the last check/rename interval.
- **Still flag if:** another UID can reach the run root; the root or staging directory is not owner-only `0700`; the record is not owner-only `0600`; the exact process-aware claim is missing, corrupt evidence is accepted, or a stopped/stale owner is recovered without verification; a non-empty destination or user bytes can be replaced; provider-controlled material can select an arbitrary filesystem target; the code claims isolation from malicious same-UID processes; or a portable/native no-replace primitive is already available in the supported runtime and the implementation still uses ordinary rename without a recorded reason.
