# Review known patterns — vegastack/vegafactory

The project's never-flag list. Every entry REQUIRES a "Still flag if:" exception clause — a suppression without one is a blind spot, not a calibration. dev-implement's corrections loop appends an entry whenever the operator dismisses a review finding, so dismissed patterns stay dismissed. Repo-documented standards override the reviewer's baseline; this file overrides neither — it only suppresses specific recurring false positives.

## `skillspector-update:` absent reads as `auto`

- **Pattern:** a reviewer flags that an absent `skillspector-update:` line resolves to `auto`, so existing `.vegastack/dev.md` profiles gain install-and-upgrade of the SkillSpector CLI without their operator having opted in — raised as a supply-chain and consent finding against `resolveUpdateMode` in `skill-scan/scripts/skill-scan.mjs`.
- **Why it's safe here:** the operator ruled on it directly after the finding was put to them with its consequences stated in full — including that downstream profiles inherit the behaviour on their next `@vegastack/vegafactory` upgrade. Keeping the scanner current is the point of the feature: a security scanner that silently rots is the worse failure, upstream ships roughly every two days, and the tool is NVIDIA's own. `off` and `notify` remain one line away, `--no-provision` covers a single run, every failure falls back to the installed copy rather than blocking, and dev-setup states the behaviour plainly when it drafts the knob.
- **Still flag if:** the default reaches beyond installing and upgrading SkillSpector itself from NVIDIA's own repository — a different tool, a different source, an install that runs as root or outside the operator's own user account, credentials or environment forwarded anywhere they were not already going, or an upgrade that proceeds where the operator wrote `off`/`notify` or passed `--no-provision`. Also flag again if the fallback stops being "use the installed copy and continue", or if a failed provision can leave the guard reporting a pass.
- **Origin:** 01-09-2026, issue #83, security axis Finding [S1] sub-point 2 — dismissed by (kmanojkumar): "make it auto even if absent".

## Unpinned SkillSpector install (tracks upstream, no ref)

- **Pattern:** a reviewer flags `INSTALL_COMMAND` in `dev-review/scripts/lib/skillspector.mjs` for installing `git+https://github.com/NVIDIA/skillspector.git` with no tag, ref or lock, and `uv tool upgrade skillspector` running before every scan — roughly seventy transitive dependencies resolved from a moving upstream HEAD.
- **Why it's safe here:** pinning is not a smaller version of this feature, it is its negation — the operator's decision is that the scanner tracks upstream, because a security scanner that silently rots is the worse failure and upstream ships roughly every two days. Pinning a ref would freeze the guard at whatever release we last hand-edited and reintroduce exactly the staleness the work removed. Measured, not assumed: `uv tool upgrade` on an already-current install takes ~2s, and it moves the dependency tree while the version string can hold steady — so there is no version comparison that could make an unpinned upgrade safer, only slower. Bounded by: NVIDIA's own repository as the sole source, `off`/`notify`/`--no-provision` as opt-outs, and a failed install falling back to the installed copy rather than blocking.
- **Still flag if:** the source is no longer NVIDIA's own repository (a fork, a mirror, a registry, a URL assembled at runtime or read from configuration), the install runs anywhere but the operator's own user account, the environment forwarded to install hooks widens beyond what the guard already inherits, or a pinned ref is introduced and then allowed to drift out of sync with the baseline's `scanner_version` without the guard noticing. Also flag if upstream's release cadence or ownership changes such that "tracks upstream" stops meaning "tracks NVIDIA".
- **Origin:** 01-09-2026, issue #83, security axis Finding [S1] — dismissed by (kmanojkumar): "dismiss the pinning one too".

## Cooperative same-UID private run-directory publication

- **Pattern:** a reviewer flags the final `lstat(destination)` followed by portable directory `rename(staging, destination)` in the private run store solely because a malicious process already running as the run-owner OS UID can create an empty destination during that final interval, and requires a native exclusive-rename helper or storage redesign.
- **Why it's safe here:** the operator selected cooperative-owner semantics for this cross-platform Node CLI after the exact residual was surfaced. The run root and staging directory are owned by the current UID with mode `0700`, `run.json` is `0600`, cooperating creators serialize through an exact process-identity claim, any destination visible at the final check is preserved, a non-empty destination makes the directory rename fail, and published bytes are read back exactly. The residual does not cross a user or provider boundary: code already executing as the run-owner UID can replace that private record after publication. Cost if the assumption is wrong: that same-UID process can have its raced empty directory replaced by the verified staged record during the last check/rename interval.
- **Still flag if:** another UID can reach the run root; the root or staging directory is not owner-only `0700`; the record is not owner-only `0600`; the exact process-aware claim is missing, corrupt evidence is accepted, or a stopped/stale owner is recovered without verification; a non-empty destination or user bytes can be replaced; provider-controlled material can select an arbitrary filesystem target; the code claims isolation from malicious same-UID processes; or a portable/native no-replace primitive is already available in the supported runtime and the implementation still uses ordinary rename without a recorded reason.
- **Origin:** 10-09-2026, issue #138, specification Finding [5] round 3 — dismissed by (kmanojkumar): "option 1".
