The worker says which worktrees could be reclaimed, and `worktree prune --write` reclaims them.

- Dependencies go first and on a shorter window than the worktree itself, under the new `worktree-deps-retention` knob. They are the cost: on the machine that prompted this, 628 MB of a 638 MB worktree was `node_modules` and the checkout itself was 10 MB — so dropping them reclaims nearly everything while the code, the branch and the history stay exactly where they were.
- Nothing uncommitted, unpushed or locked ever loses anything, dependencies included, and a worktree a run is holding is skipped whole. The worker's pass is deliberately narrower than the `prune` a person runs: it never pushes a branch and never commits anything as `wip`, because a person asked and can be told "your work is on a branch" while a background pass has nobody to tell. What it will not touch is reported through the worker's own notes rather than silently skipped.
- `gh --paginate` prints one JSON document per page, and they are now read as the one list the caller asked for. A single parse failed the moment a repository had more than a hundred open issues, which made the closed-issue check silently see nothing at all.
- A worktree whose issue is closed is finished, and does not wait out a window meant for work that might still be wanted. Merged ones are the same. Every refusal still applies to both.
- Dependencies git tracks are never deleted. A repository may legitimately commit something under `node_modules` — a patched package, a vendored stub — and `git status` is clean either way, so without the check the sweep would have removed committed files.
- What was kept is named at the moment it could have gone, rather than eleven days later when the whole-worktree window elapses.
- The record of a drop is one file per worktree. A single shared document is read, changed and written back, so a pass clearing one worktree and a pass recording another could lose each other's entry — leaving a checkout with no dependencies and nothing saying they were taken.
- The Linux unit sets `UMask=0077` and the worker's directory is owner-only. Those files hold the tail of every agent's output — private repository text, and the short-lived token a run was given — and systemd would otherwise create them against whatever umask it inherited.
- A checkout whose dependencies were taken says so, and names the `setup` command to put them back. The drop is recorded beside the repository's worker state — outside the checkout it describes, which a deps-only prune leaves in place — and removing a worktree forgets it, so a name that comes back is not told about an install that never happened. Running that command as part of the build that needs it is #275; a fresh worktree still installs nothing, so a docs-only issue stays cheap.
- The report rides in the poll pass rather than on a schedule of its own, so there is one thing to reason about and one place it appears. It removes nothing: doing that on its own would need the pass to know which checkouts somebody is sitting in, and nothing tells it — the run map is blind to attended sessions, a file's mtime does not move for someone reading and building, and git's worktree lock is not reference-counted, so two sessions in one checkout have the first to end release the other's hold. `vegafactory worktree prune --write` stays the way a worktree is reclaimed, run by a person who knows what they are in.
