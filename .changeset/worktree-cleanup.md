`vegafactory worktree prune --write` reclaims what idle worktrees are holding, dependencies first.

- Dependencies go first and on a shorter window than the worktree itself, under the new `worktree-deps-retention` knob. They are the cost: on the machine that prompted this, 628 MB of a 638 MB worktree was `node_modules` and the checkout itself was 10 MB — so dropping them reclaims nearly everything while the code, the branch and the history stay exactly where they were.
- Nothing uncommitted, unpushed or locked ever loses anything, dependencies included. Every refusal that protects a worktree protects what is inside it.
- A checkout whose dependencies were taken says so wherever it is described — `worktree list`, `worktree status` and the prune itself — and names the `setup` command that puts them back. The record of the drop lives beside the repository's worker state rather than inside the checkout, because a deps-only prune leaves that checkout in place; removing a worktree forgets it, so a name that comes back is not told about an install that never happened.
- A prune no longer recreates a branch somebody deleted, and no longer refuses to reclaim its worktree. Delete-on-merge removes the feature branch, and the merged-ness test used to skip its ancestry check entirely whenever the remote ref was gone — so a merged worktree read as both unpushed and unmerged, had its deleted branch pushed back, and then stayed. Ancestry now counts when the base has moved past the branch, which is the precise version of "its commits were taken in" and still declines to call a branch cut this morning merged.
- Dependencies git tracks are never deleted. A repository may legitimately commit something under `node_modules` — a patched package, a vendored stub — and `git status` is clean either way, so without the check the sweep would have removed committed files.
- A worktree whose issue is closed is finished, and does not wait out a window meant for work that might still be wanted. Merged ones are the same. Every refusal still applies to both.
- What is kept is named at the moment it could have gone, rather than eleven days later when the whole-worktree window elapses.
- `gh --paginate` prints one JSON document per page, and they are now read as the one list the caller asked for. A single parse failed the moment a repository had more than a hundred open issues, which made the closed-issue check silently see nothing at all.
- The record of a drop is one file per worktree. A single shared document is read, changed and written back, so a pass clearing one worktree and a pass recording another could lose each other's entry — leaving a checkout with no dependencies and nothing saying they were taken. A record that cannot be read is reported rather than read as "nothing was taken", which is the one answer that leaves a broken checkout looking untouched — and the records are names and nothing else, because reading their contents would be a way to print whatever a planted symlink named.
- The Linux unit sets `UMask=0077`, and the worker's directory and every record in it are owner-only. Those files hold the tail of every agent's output — private repository text, and the short-lived token a run was given. The directory is created 0700, set 0700 on an upgrade, and refuses a symlink because `chmod` follows one; each record is checked too, because an account that could write the directory before it was tightened can leave a link named `runs.jsonl` or `children.json` behind, and append, read and replace all follow one.
- `worktree prune --dry-run --write` previews instead of acting. Flags were applied in the order they were typed while the guard that decides whether to ask looks for `--dry-run` anywhere, so that line acted while being waved through as a preview.
