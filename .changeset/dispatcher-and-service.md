New `vegafactory dispatch enable|disable|status|run`: a machine that works the board with nobody at the keyboard. It refuses every verb but `disable` unless the org control room's `dispatchers.md` names this machine, so enrolling and standing a machine down are both control-room PRs. `enable` checks the row, the harness hooks on both tools, a real `claude -p` and `codex exec` answering on their subscriptions, and the GitHub App key, then installs the launchd (macOS) or systemd (Linux) unit; a failed check installs nothing and names what to fix. `status` prints the board plus this machine's recent runs, and `run --once` makes a single pass.

Identity is the VegaFactory GitHub App. The dispatcher mints an hour-long installation token from the private key on the machine (`~/.vegastack/vegafactory-app.pem`, moved by `VEGAFACTORY_APP_PRIVATE_KEY_FILE`; `VEGAFACTORY_APP_ID` names another org's App), narrowed to the one repository, kept in memory and handed to `gh` in that child's environment only — never written down, never printed, never on a command line. A missing key refuses with the path to fix and never falls back to a person's token. A comment from `vegafactory[bot]` now counts as a claim holder or a claim release, so a dispatcher's work is visible to every session; it still counts for nothing as an ack, a "ship it" or a review.

Each dispatched run starts with `VSK_ASK_ROUTE=issue`, so a round of questions goes to the issue and waits there for the operator instead of reaching for a question tool nobody is watching, and the plan's `**Independent groups:**` block is now read rather than merely recorded: the dispatcher is what runs disjoint sibling sub-issues at the same time.

The loop reads the board every two minutes through the issue cache, so an unchanged issue is nearly free, and runs at most three steps at once: an operator comment on `waiting-on-operator` is a follow-up, `planning` is a plan (a `large` issue splits into sub-issues under an `epic`), `queued` is an implement run that reviews and hands back on `ready-to-ship`, an operator comment on `ready-to-ship` is either corrections or — when they say "ship it" — a ship, "stop" saves the work, pushes it and releases the claim, and a subscription limit does the same with a note and retries after the reset. Each trigger runs once; a failed step backs off and is parked for a person after three tries. An issue with a fresh claim is skipped, a step is killed after 20 minutes, merges go one at a time, tasks inside an issue run in order, and two code runs happen together only for sibling sub-issues whose parent plan declares disjoint file sets — never on generated code, migrations, lockfiles or `package.json`. Every child run goes through the subscription check, so an API-key variable in the environment refuses the command, and each run's own output is bounded and recorded on the machine rather than posted to the issue.
